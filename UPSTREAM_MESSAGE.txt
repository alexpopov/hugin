Subject: macOS: Tip-of-the-Day deadlock on Rosetta — root cause and 5-line fix

Hi,

I traced the long-standing "Hugin freezes on launch under Rosetta on
recent macOS" issue (which led to the Homebrew cask being deprecated
and disabled) down to a specific synchronisation problem, and have a
small patch I'd like to upstream.

== Symptom ==

On Apple Silicon Macs running macOS 14+, launching Hugin (any x86_64
build, e.g. the deprecated Homebrew cask) hangs at startup. The
Tip-of-the-Day dialog is supposed to appear but never paints; the app
sits at >100% CPU and never reaches the main window. Existing
workarounds — disabling the tip via /MainFrame/ShowStartTip=0 in the
prefs file — don't take because the user can't dismiss the dialog
that fails to render in the first place.

== Root cause ==

huginApp::OnInit calls frame->OnTipOfDay(dummy) synchronously, before
wxApp::OnRun starts the main event loop:

    src/hugin1/hugin/huginApp.cpp:~636
        if(nValue > 0)
        {
            wxCommandEvent dummy;
            frame->OnTipOfDay(dummy);   // ← synchronous, pre-mainloop
        }

That spawns a *nested* AppKit modal session in a pre-mainloop context.
On native arm64 this works fine; under Rosetta it deadlocks inside
CoreAnimation's CABackingStoreGetFrontTexture, which does a sync
dispatch to the RenderServer queue. Across the x86_64↔arm64 translation
boundary the dispatch queue ownership lookup never returns:

  main → wxEntry → wxApp::CallOnInit → huginApp::OnInit
    → frame->OnTipOfDay → wxShowTip → wxDialog::ShowModal
      → wxModalEventLoop::OSXDoRun → NSApplication runModalSession
        → CA::Transaction::commit → CABackingStoreGetFrontTexture
          → _dispatch_sync_f_slow
            → _dispatch_event_loop_wait_for_ownership  ← stuck

Empirical confirmation on my Apple Silicon Mac:

  1. With ShowStartTip=1 (default), the cask Hugin under Rosetta
     deadlocks. Sampled stack matches the above exactly.

  2. With ShowStartTip=0 (forced via prefs file edit, since the dialog
     can't be dismissed), the SAME binary runs healthily. Sampled
     stack lands cleanly in wxApp::OnRun → wxAppConsoleBase::MainLoop
     → NSApplication run → _DPSNextEvent → mach_msg (idle).

So the deadlock is specifically the modal-during-OnInit pattern under
Rosetta, not any other macOS 14+ change.

== Fix ==

Defer the tip invocation to the next event loop iteration via
frame->CallAfter(...). By the time the lambda runs, OnInit has
returned, wxApp::OnRun is active, and the modal dialog opens in a
normal AppKit modal session context — identical to how the existing
Help menu → "Show Tip of the Day" invocation has always worked.

  if(nValue > 0)
  {
      frame->CallAfter([this]() {
          wxCommandEvent dummy;
          frame->OnTipOfDay(dummy);
      });
  }

5-line change. Tested on native arm64 (no regression in tip display
behaviour). I couldn't trivially test the patched x86_64 binary under
Rosetta on my machine without a full x86_64 build, but given (1) the
deadlock is empirically the modal-in-OnInit pattern and (2) CallAfter
posts the same call to the post-OnInit loop context, the fix should
resolve it. Happy to do the x86_64 build to confirm if you'd like.

This patch would in effect un-break the Homebrew cask for every
existing user on macOS 14+ without any rebuild on their side.

== Separately, native arm64 build ==

While diagnosing, I also did a from-source native arm64 build using
Homebrew dependencies (it's the only path I could find that works
today; the mac/ExternalPrograms/scripts/ flow needs some refresh —
broken download URLs, Intel-only -march/llvm paths in SetEnv.sh).

That work resulted in two more small patches I'd like to upstream
separately if you're interested:

  - Bump CMAKE_OSX_DEPLOYMENT_TARGET from 10.9 to 11.0 (Hugin's own
    std::filesystem usage requires 10.15+; 11.0 is the Apple Silicon
    floor anyway).

  - Decouple the runtime bundle tool-lookup
    (MacGetPathToBundledExecutableFile) from MAC_SELF_CONTAINED_BUNDLE
    so that non-self-contained Homebrew-deps builds can still find
    their own CLI tools inside Hugin.app/Contents/MacOS/.

These are smaller and less critical than the tip-of-day fix, but the
combination of all three is what made a working arm64 build possible
for me. Code visible in my mirror branch at:
https://github.com/alexpopov/hugin/tree/macos-arm64-build

I'd send the tip-of-day patch first as a discrete PR/ticket since it
fixes a user-visible regression. The two arm64 patches could follow
together as a "build path also works with Homebrew deps" change.
Refreshing the mac/ExternalPrograms scripts to actually produce a
modern self-contained .app on Apple Silicon is a much bigger job that
I'd love to take on if it'd be welcome, but want to align with you on
direction before sinking time into it.
